# 终极人机采集、训练与验收方案

2026-11-25 · 设计稿

**目标是做一个能代替官网终极人机陪队友练习的本地对手。** 给它相似的地图、局面和对手打法，它应以接近官网的频率靠近、退开、出手、躲弹和犯错。参赛策略另按官网四档 40 局总分验收。陪练的胜率、我方命中率和整局时长都能帮助诊断，其中任何一项单独升高都不能证明还原度提高。

**第一轮只研究“首次近身后，官网什么时候主动拉开”。** 固定 v31 为对照，保留它的起步、开火和避弹能力。交付一份带正负例的近身事件集、一个只替换交战走位的候选，以及一张说明它在哪些条件下更像官网的对照表。后续按同一流程验证其他行为。

现有工作台可复用官网队列、按图冻结的常驻调度、回放归档、动作反推、短程复跑、SDK 整局对打和版本快照。本方案新增的核心是逐次机会表、固定参考与干预编排、局部训练候选、统一的能力验收和选版规则。

## 1. 为什么这样改

| 已有证据 | 设计决定 |
|---|---|
| 36 场盲测中，v35 的开火时机 F1 从 0.844 提升到 0.866，存亡判错从 11 局降到 8 局，整局时长误差却从 14.52 秒升到 14.96 秒。 | 分别决定是否保留某项改进、是否替换全队默认陪练。 |
| 固定模型和开发图，训练布局从 24 张增至 48、72 张，两秒走位误差依次约为 1.37、1.34、1.33 格。轨迹版当前只在决定不开火的帧调整走位。 | 先查候选能否表达官网动作、选出的动作有没有真正执行，再决定补数据还是换模型。 |
| 冻结的 388 场训练回放覆盖 72 张图。266 场进入过三格；首次出现“三格内官网中弹、双方当帧仍存活”的有 180 场、59 张图。随后三秒内官网主动拉开 4 场，看满三秒未拉开 148 场，窗口提前结束 28 场。 | 分开数有机会观察、实际发生、观察中断。以前的“8 张图出现过这种行为”统计整局任一次命中，两种数字用途不同。 |
| 同图、同侧、同打法、同局号的 16 对官网重复练习中，时长差绝对值中位数为 4.85 秒，2 对的赢家不同。 | 用官网下载的重复回放估计同条件波动，按行为分别校准，4.85 秒不通用于其他指标。 |

走位与开火分开做受控实验，借鉴 MLMove；相似局面检索基线借鉴 FightingICE。短窗口复演、官方游戏计分和近身事件定义沿用本仓实测。[对战实验调研](./对战策略与陪练实验调研.md) · [已有版本对照](./终极档行为复现实验.md) · [MLMove 论文](https://doi.org/10.1111/cgf.15173) · [FightingICE 论文](https://www.ice.ci.ritsumei.ac.jp/~ruck/PAP/ieeeCIG2014.pdf)

## 2. 常驻采集怎样排

采集号继续通过官网练习入口对阵终极档。工作台保存每张图的种子、打法快照、红蓝侧、重复编号和排局原因；队友需要同一席位时先让位，恢复时只补缺场。每局以官网对局 ID 去重，原始回放保留内容哈希。规则或 SDK 变更后分批记录。沿用现有常驻任务和断点，让新规则在下一张尚未排定的图生效。[现有采样入口](./在线采样.md)

**训练图建议先按八张一个周期。** 每张三组，每组红蓝各一局，合计 48 局。每张保留一个参考打法，在事先冻结的专项、游击快照间平衡轮换。其余两组按下表分配。

| 张数 | 怎样打 | 解决的问题 |
|---:|---|---|
| 4 | 按训练库的缺口选两种打法。例如拉开再接近、绕墙探头、倒车撤退、拖到缩圈。 | 优先增加独立地图上的合格机会，同时补少见的反应和反例。 |
| 2 | 同一导航和触发条件，一组开火、一组停火。按地图随机安排先后顺序，两组均换边。 | 区分“看见来弹才躲”和“到了这个距离本来就转”。 |
| 1 | 留给很少试过的打法或两种模型预判不同的条件，只按训练数据挑。 | 给现有采样规律之外的行为留入口。 |
| 1 | 一组复打本图参考打法，固定快照、出生侧和官网局号；另一组补当前缺口。 | 量出同条件重复时的波动，包括联机时序影响。 |

采集器为每个目标记录“合格机会、发生、完整未发生、提前结束”各覆盖多少张图，再选择最可能补到缺项的打法。每一项都能追溯到回放。连续两个训练周期没有新图触发目标，就检查触发条件和探针；有大量机会却极少发生，就检验它是否本来就少见。低命中探针适合研究躲弹，有效命中探针适合研究中弹后的反应。

**验收另留固定对手组合。** 采样前用 SDK 根据种子生成布局，查询已有保留清单和地图分组。新布局沿用现有哈希十桶，八桶训练、一桶开发、一桶盲测。归档以官网实际墙面哈希为准，预判不符的对局不能进入原计划的配对验收。相同布局的换边、重复和切片始终同组。新盲图还须排除基座或其前身已用于训练、开发的布局。开发图可用于诊断选型，盲测图和预留的整类探针不参与训练调度、检索、标准化或选模。同一导航的换名或微调版本归入同一打法族。固定验收组合按预定地图和打法执行，补缺池的行为频率只描述补缺池。

做官网开火／停火对照时，两组从同一个预先定义的可开火机会计时。入场距离、朝向或退路不匹配，仍记录为覆盖样本，退出因果对照。

## 3. 从回放得到可训练的样本

- **一局保留一份事实。** 记录官网目标身份和所在侧、我方快照、地图布局、局号、SDK 与规则、完成原因及可用的动作时序。缺我方快照的历史回放仍可用于可验证的官方行为标签，精确整局对打只用能还原对手的记录。
- **一个机会一条记录。** 记录对局 ID、触发帧、观察结束帧、当时可见历史、场景、官方反应、结果是否完整。同一次接战连续几十帧只计一次。首轮主分析每局取第一次合格机会，后续再接战单列。未来帧用于打标签，模型推理只读当时 SDK 可见的内容。墙体遮挡描述弹道是否通畅，双方位置按 SDK 的全局可见规则处理。
- **三秒撤退口径。** 从首次进入三格开始；“近身中弹”另从首次确认非致死命中开始。双方仍存活、距离增至至少五格且官网移动净贡献至少一格，记为主动拉开。距离变化按双方位移分别归因。看满三秒仍未达到条件记为未拉开；一方阵亡、到时结束、数据缺失各有结局。触发瞬间就致死的命中进入伤害统计，没有“中弹后反应”机会。[已有位移归因](../src/tank/sampling_probes.py)
- **动作分量单独定真值。** 位置变化能确定的进退、转向，以及成功出弹的帧可作标签。贴墙不动时可能仍在推墙；冷却期间看不到开火意图。保留不可辨识标记或等价动作集合，其他可确认分量仍训练。先用有真实输入记录的本地策略校准还原精度，再用官网双方反推动作回放校准时序。把未知进退临时置零以推进 SDK，只能用于条件复演，不能回写为训练标签。[训练端的动作反推](../training/fit_boss_sparring.py)

## 4. 怎样训，怎样发现瓶颈

1. **建立两个基线。** v31 代表现有可用陪练。另做按距离、朝向、退路、来弹和最近移动检索的简单基线，从训练图抽取相似局面之后真实发生的反应。再报告“总不撤”等常数预测，以暴露稀有事件带来的虚高准确率。
2. **首轮只替换交战走位。** 从短历史预测继续压近、主动拉开、保持交战等可观察反应及其可能性，并产生能在 SDK 执行的短动作序列。比较首选和固定三个候选中最接近官网的一条。三条都偏，先查数据和动作表达；仅首选偏，查排序；选对但执行偏，查开火、避弹和动作复用是否覆盖了它。真实结果只用于事后诊断。
3. **同一输入做消融。** 在相同地图、对手、预算下比较 v31、仅换走位、仅换开火控制、以及两者组合。开火帧与非开火帧分别检查移动。如果某个能力只能在底层避弹接管后才表现出来，把接管前后动作都记录下来。不同预测路线的概率用独立开发图校准，整局滚动时保留短期行为连续性。
4. **边采边训按新信息触发。** 每八张训练图结算覆盖。建议首轮达到“本阶段新增 12 张有目标机会的图，或新增 8 张出现稀有正例的图”才开下一次训练；同一冻结数据、代码、配置和种子复用原作业。按地图和局面平衡训练，固定验收集保持原来的分布。两轮扩容都只改善离线误差时，先做第 2 步的瓶颈诊断，再追加同类数据。模仿陪练的更新信号来自官网行为，参赛策略的强化学习收益单独记录。

**首版训练配方。** 用现有逐帧特征加半秒可见历史，与“只看当前帧”对照。用训练回放中可还原的连续进退和转向片段构造候选，在 SDK 中回放这些片段；轻量分类器学习在当前观测下选择哪个候选。发生与否用所有合格机会监督，时机只用观察到该反应的片段，动作损失跳过不可辨识分量。训练批次可以多抽少见行为，开发集另查预测撤退概率是否与实际频率一致。按 0.3、1、2 秒检查候选路线，每帧重读观测；近身阶段结束后交回 v31。检索基线若已达到同等效果，保留更简单的版本。

## 5. 评判维度与分母

每个行为都回答三个问题：**进得去这种局面吗？遇到时怎么反应？反应之后产生什么结果？** 从未近身可能是前段走位失败。这局计入“创造近身机会”，不计入“近身后是否撤退”的分母。指标一律注明官网人机侧或我方探针侧。

| 能力 | 从哪里开始数 | 主要比较什么 |
|---|---|---|
| 起步与导航 | 出生、首次有通路、接近墙边；正常时序与延迟起步分层 | 起步时间、前两秒位移、卡墙时长、首次取得可交战位置的时间 |
| 接近、撤退与再接战 | 首次近身；首次非致死近身中弹；完成分离后 | 机会数、主动退开的比例、漏撤和误撤、首次拉开时间、是否返回三格内；血量落后、贴墙、出生侧分层 |
| 开火与瞄准 | 达到可开火条件的窗口，以及每次实际出弹 | 出手与停火的符合率、时机偏差、分距离的方向偏差、命中／出弹、每局命中数以及实际承伤 |
| 对来弹的反应 | 官方在途可见、可归因的危险来弹；另设同条件无威胁窗口 | 官网躲过和被击中分别报符合率；观察到来弹后几帧开始移动、方向与位移、无威胁时有无误躲。出膛同帧即中另报 |
| 缩圈与位置取舍 | 双方进入缩圈阶段或首次接近圈边 | 回圈时机、圈内位置被让出、圈外停留与掉血。按是否活到该阶段另计机会，区分圈伤和炮击 |
| 整局交互 | 固定地图、探针、侧位、局号的完整对局 | 交战距离分布、双方命中／承伤、首次中弹、存亡和死因、时长及游戏分项；不同打法分别展示 |

事件先报发生／未发生，再算双方都发生时的时间误差。提前结束保留为竞争结局或截尾，单列发生率，不塞进负例。路线、距离等共同存活指标旁列活到各时点的比例。正例和负例分别报覆盖图数，避免“全部预测不撤”在稀有局面获得高分。

### 同一候选经过的三次检查

| 检查 | 实验方法 | 能支持的判断 |
|---|---|---|
| 同局面短窗口 | 从官网同一帧还原状态，给模型相同历史。先用双方原动作检查还原误差，再固定或逐帧校正对侧官网轨迹，让陪练走 0.3、1、2 秒；撤退事件延长到 3 秒。 | 找出首次偏差，区分触发、选路和执行。对侧轨迹已被固定，只解释给定轨迹下的反应。 |
| SDK 自由对打 | 同一探针快照从开局自由响应，候选和 v31 同图同侧同局号；用预定重复和时序压力各跑一次。 | 检查小偏差是否累积成过早贴脸、连吃伤害、让圈或提前死亡。 |
| 官网独立对照 | 固定探针组合在新图练习，保留同条件重复。需要验证“因开火而退”时，使用第 2 节的开火／停火配对。 | 衡量独立参考下的还原度与官网自身波动。历史录像仅能验证当时实际发生的分支。 |

## 6. 如何决定保留能力、替换默认、宣称高还原

**先校准评测。** 用行为已知的本地策略做回放，分别注入晚两帧开火、推迟撤退、遇弹错选方向三种变化。相应短窗口指标应能指出改了哪项，并报告未改行为的波动。首轮规则写入一份可执行配置，报告和通过判定读取同一份；过去的实验说明提到近身走位保护，选版脚本实际只将它用于开发集平局排序。

**再冻结判据。** 基线、候选、样本清单、对手族、事件定义、主指标、容许退步幅度和最小支持量都在揭盲前锁定。先在开发图上筛一个候选。计算同图候选减 v31 的误差差值，换边和重复先在图内汇总，再按图等权估计 95% 配对区间。一个地图多个窗口仍是一张图。比较两项比例用百分点，距离用格，时间用秒，基线为零时仍可比较。

| 结论 | 建议的首轮判法 |
|---|---|
| **保留专项改进** | 在共同参考锚点，主指标取“漏撤率与误撤率的等权平均”，用事先固定的反应判定。建议实际改善至少 5 个百分点，且差值区间上界低于零。并检查非近身误触、早死和提前结束。允许保留仅在指定条件下有效的快照。 |
| **替换默认陪练** | 冻结候选在未见地图上通过主项，再查固定探针组合的保护项。首轮可用交战距离误差增加 0.25 格、开火／避弹或存亡分歧增加 5 个百分点作为待校准的容许上限；误差差值区间上界须在各自上限内。时长按对手打法和死因解释，开发期依据重复练习另定有实际影响的上限。单一总分不参与投票。 |
| **证据不足** | 首轮正式确认先预留至少 20 张新布局；某一类正／负反应若覆盖不足 10 张独立布局，该类结论待补。数量只是开评下限，区间仍宽就维持原默认。盲测揭晓后的图标为“已用验收”，下一次调参后的候选用新图确认。 |
| **高还原** | 同一布局、打法、侧位内，计算“陪练对官网的平均差距”减去“不同官网重复之间的平均差距”，所有预定重复都计入。按固定参考打法和额外预留打法分别验收。关键维度的额外误差区间上界落入事先约定的容许范围，且正负覆盖足够，才给出对应场景的高还原结论。只通过局部的，就写明具体能力。 |

这些数值是初始设计参数。先用已知扰动验证辨别力，再结合独立重复练习和团队能接受的误差定稿。调度的八图周期、训练触发量和揭盲条件分别控制成本、数据增量和证据强度，不混用。

## 7. 工作台、协作与开发顺序

「结果」页优先回答**现在用哪版、哪项比上版更像、下一批缺什么局面**。点开能力能看到官网与本地数值、独立地图数、正负机会数及一组同条件回放。不同版本留历史。GPT 复用现有采样状态／导出、训练作业和策略快照；拟补的结构化输出包括机会统计与采样原因、训练清单与快照、逐图差值与区间、版本判定及原因。新回放归档和训练作业完成时由现有工作进程触发下一步，进度随任务 ID 落盘，可断点续跑，无需 GPT 常驻或系统定时任务。原始回放和临时产物留在主机，团队交接用 Git 共享选定的快照、数据清单和报告。

| 顺序 | 谁负责 | 交付与完成条件 |
